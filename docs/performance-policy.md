# Требования к производительности

Производительность входит в критерии качества решения. Общая инструкция «код должен
быть быстрым» непроверяема: требования нужны для конкретного сценария и нагрузки.
Комплект разделяет короткое [общее правило](../codex-kit/.codex/rules/performance.md)
и численные бюджеты целевого проекта в [project.md](../codex-kit/.codex/project.md).
Правило читается по влиянию задачи; отдельный агент по производительности не требуется.

## Что заполнить в проекте

Для каждого критического сценария достаточно строки или ссылки на существующий тест:

| Поле | Что зафиксировать |
|---|---|
| Операция и границы | Например, от нажатия до отображения результата, включая сеть |
| Нагрузка и данные | Интенсивность, конкурентность, размер и распределение данных |
| Цели | Нужные процентили задержки, успешная производительность и доля ошибок |
| Ресурсы | Пределы памяти/CPU/I/O, очередей и соединений, если существенны |
| Проверка | Команда, длительность, прогрев, стенд, артефакт результата |
| Приёмка | Абсолютные бюджеты и допустимая регрессия относительно baseline |

Не все метрики обязательны для каждой задачи. Для импорта важны время завершения,
память и поведение на больших данных; для UI — отзывчивость; для API — задержка
и успешная пропускная способность при заданной нагрузке; для очереди — возраст
ожидающих задач и способность обработать поступающий поток.

Если требований ещё нет, агент может снять исходные показатели и предложить числа.
Они остаются предложением до принятия владельцем; текущая медленная реализация
не становится приемлемой только потому, что новая не медленнее неё.

## Соразмерный процесс

Документация и косметика не запускают нагрузочный цикл. Изменение SQL, алгоритма,
объёма ответа, кэша или параллелизма требует оценки влияния и подходящей проверки.
Оптимизация требует сопоставимых замеров до/после. Критический путь или риск перегрузки
требуют проверки на уровне затронутой системы. Уже предусмотренный reviewer проверяет
критерии и доказательства; отдельный полный цикл агентов не добавляется.

Это требования к будущей работе, а не подтверждение ускорения DataMatrixControl.
Для DMC ещё предстоит определить сценарии и бюджеты на представительном стенде;
численные SLA, настройки оборудования и версия приложения сюда не переносятся.

При выборе метрик использован первичный источник:
[Google SRE: Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/).
Он объясняет совместный учёт задержек, нагрузки, ошибок и насыщения, разделение
успешных и ошибочных ответов и необходимость видеть медленный хвост распределения.
Условная загрузка правил и порядок приёмки — решения этого комплекта.
