# UI как отдельная специализация

Добавлены две роли, а независимое ревью осталось общим. Разделение полезно тем,
что дизайн определяет путь пользователя и визуальное решение, а реализация отвечает
за работающий интерфейс, поведение и проверку на целевой платформе.

| Роль | Профиль | Результат |
|---|---|---|
| `kit_ui_designer` | `gpt-6.1-sol / medium` | Сценарий, структура экранов, состояния, компоненты/токены и критерии; схема/спецификация либо прототип |
| `kit_ui_developer` | `gpt-6.1-terra / medium` | Реализация в стеке проекта, поведенческие проверки и проверенный рендер |
| Существующий `kit_reviewer` | `gpt-6.1-sol / high` | Независимая оценка готового изменения, включая UX, доступность и интеграцию |

Это профили для начала работы, а не доказанная оптимальная комбинация моделей.
Число ролей стало восемь; навыков по-прежнему пять. Отдельные frontend-reviewer,
UX-аудитор, тестировщик и стилист на каждую задачу не добавлены.

## Маршруты

- **Нет достаточного решения для экрана/пути/стиля:** designer → UI developer → проверки/интеграция → reviewer.
- **Реализация по достаточному готовому дизайну:** UI developer → проверки/интеграция → reviewer.
- **Малая безопасная правка существующего текста/стиля:** основная сессия и проверка по риску.
- **Локальный UI-баг с готовым решением:** основная сессия либо UI developer и независимый reviewer;
  дизайнер и отдельное планирование не обязательны.
- **Запрошена только концепция:** designer и передача результата; реализация автоматически не начинается.
  Схема/спецификация допустима прямо в ответе без файлов; при недоступном делегировании
  основная сессия может подготовить её с явным указанием ограничения.
- **UI и backend:** после общего контракта UI developer и developer могут работать параллельно,
  если области записи разделены, а конфликтующие проверки изолированы/последовательны.
  Лимит двух пишущих исполнителей учитывает основную сессию и дизайнера.

Прямой запрос на UI маршрутизируется через AGENTS и dev-cycle; новый обязательный
skill не нужен. Конкретные условия — в [UI-workflow](../codex-kit/.agents/skills/dev-cycle/references/ui-workflow.md).
Субагенты не оркестрируют друг друга. История, Git-владение и TDD остаются общими.

## Что означает «учитывать мировые практики»

Правила в [ux-ui.md](../codex-kit/.codex/rules/ux-ui.md) требуют понимать задачу и контекст,
сохранять стиль проекта, применять визуальную иерархию и проверять удобство на сценариях.
Здесь нет универсального «модного оформления», одинаково подходящего для операторского
терминала, финансового кабинета и публичного сайта.

Использованы первичные источники:

- [Эвристики Nielsen Norman Group](https://www.nngroup.com/articles/ten-usability-heuristics/):
  понятность статуса, язык пользователя, предсказуемость, предотвращение ошибок,
  возможность восстановления и отсутствие лишней сложности. Это ориентиры оценки,
  не доказательство удобства для конкретной аудитории.
- [WCAG 2.2](https://www.w3.org/TR/WCAG22/): проверяемые требования к доступности web-контента.
  Для изменяемого web UI принят ориентир AA; для desktop используются возможности
  платформы. Проверка отдельной области не означает сертификацию всего приложения.
- [Основы Material Design](https://m3.material.io/foundations/): единые значения стиля
  через design tokens. Это полезный принцип согласованности; Material не становится
  обязательным внешним видом или зависимостью проекта.

Существующий [client.md](../codex-kit/.codex/rules/client.md) продолжает определять
отзывчивость, длительные операции, ошибки, отмену, offline и гонки ответов. Эти требования
не продублированы в новом правиле. Дизайн должен показать применимые состояния, а не
только красивый экран с успешными данными.

## Что передаётся между ролями

Одно конкретное решение: пользовательская задача, структура и основные действия,
переходы/состояния, используемые компоненты, стиль, адаптация размеров/ввода и критерии.
В существующем проекте предпочтительны ссылки на его компоненты и токены. Отдельный
длинный дизайн-документ не обязателен; достаточно раздела плана или компактного артефакта.

Например, для рабочего списка заказов учитываются поиск, приоритет столбцов, длинные
значения, клавиатура, выбор и массовые операции, а не только оформление карточек.
Набор решений определяется реальным сценарием и контрактом API.

UI-разработчик проверяет рендер и взаимодействия на представительном содержимом;
скриншот не доказывает работу клавиатуры, а проходящая сборка — удобство интерфейса.
Недоступность запуска/рендера остаётся явным ограничением. Тестирование с настоящими
пользователями требуется по риску и не заменяется выдуманными персонами/метриками агента.

В `.codex/project.md` добавлены поля для аудитории, платформ/размеров, стиля и команд
UI-проверки. Реальный UI и дизайн-система DataMatrixControl в этом изменении не создавались.
