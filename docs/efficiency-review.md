# Разбор исходной настройки Codex DMC

Проверены только `.agents/skills/` и инструкции ролей Codex. Конфигурация Cursor
не оценивается и не изменяется. Показатели ниже относятся к файлам, а не к замеру
токенов реальной разработки.

## Что сохранить

- Независимое ревью и возврат конкретных замечаний автору изменения.
- Ограниченный scope, критерии готовности и зависимости в плане.
- Параллельность только независимых областей и последовательность связанных работ.
- Отдельная забота о пользовательских инструкциях и точности документации.
- Возможность продолжать сохранённый план, сохраняя завершённые пункты.
- Проверки результата и запрет незаказанных commit/push.

## Где расход не окупается

| Исходная настройка | Последствие | Решение в комплекте |
|---|---|---|
| Любая подзадача проходит developer → reviewer → tech-writer | Повторное чтение одного контекста, высокая цена мелких пунктов | Пакеты проверяемого поведения; документация после стабилизации |
| Основной агент никогда не пишет код | Даже простая правка требует передачи контекста | Прямой путь для малых низкорисковых правок |
| Модель наследуется для всех ролей | Простые тексты могут выполняться моделью и effort основной сессии | Явные профили на каждую роль |
| Backend/frontend дублируют почти одинаковые процессы | Больше инструкций, сложнее mixed-задачи и интеграция | Одна роль реализации и одна роль ревью с предметными проверками |
| Три документатора, включая обязательный финальный | Перекрытие ответственности и повторные обзоры | Один документатор по потребности, обе аудитории |
| До 15 циклов исправления/ревью | Возможен длинный спор без смены подхода | Два раунда, затем адресный expert и одна проверяемая попытка |
| Общий CHANGES.LOG разрешено писать параллельно | Конфликты и потерянные записи | Один владелец общих файлов |
| Проверка отдельных пунктов без явного общего прохода | Риск пропустить дефект между компонентами | Ревью стабильной связанной области и интеграционных границ |
| Общие советы о SOLID, типизации, шаблоны длинных ответов | Увеличение контекста без проектной информации | Короткие роли и отдельный project.md |
| Расчёт шкал по каждому уровню и разные шаблоны плана | Работа над состоянием плана вместо результата | Один простой шаблон; существующий формат сохраняется |
| Качество, bugbot и security разделены исключениями | Существенный дефект может оказаться «чужой» ответственностью | Ревью включает реальные риски изменённого кода |
| Ревью ветки относительно default base по умолчанию | Можно получить огромный несвязанный diff | Scope из запроса; для обычного ревью — текущие изменения |

Планирование, explorer и expert не обязательные фазы. Дополнительный агент должен
дать независимость, изоляцию большого контекста или полезную параллельность.
Параллельность прежде всего сокращает время; сама по себе она не экономит токены.

## Структурное сравнение запусков

Пусть N — число исходных подзадач. Для новой задачи старый цикл без исправлений:
`1 planner + N developer + N reviewer + N tech-writer + 1 user-doc-writer = 3N + 2`.
Для готового плана planner отсутствует. Это число назначений ролей, а не доказанный
расход: разные запуски могут иметь разный контекст и повторно использовать сессию.

Пример с шестью независимыми результатами, объединёнными в два проверяемых пакета:
старый процесс — 20 назначений; новый возможный — planner + два developer + reviewer
+ documenter = 5. Если нужны отдельные ревью, больше документации или исправления,
число вырастет. Для малой правки возможно 0 субагентов; для обычной — developer
(или основная сессия) + reviewer. Риск важнее числа строк.

## Ограничения оптимизации

Меньше ролей не всегда означает лучше: сложный фронтенд, миграция, протокол устройства
или большой незнакомый модуль могут требовать более сильного effort и отдельного
исследования. Дешёвый запуск, после которого всё приходится переделывать, увеличивает
общую стоимость. Поэтому качество критериев, регрессионных тестов и полнота результата
важнее минимального числа вызовов.

В исходном наборе семи навыков разработки и их ссылок: **24 файла, 76 213 символов**.
Это суммарный объём, не объём каждого запроса: навыки загружаются выборочно.
Результаты измерения нового комплекта и проверки — в [validation.md](validation.md).

## Что измерять на реальных задачах

Сравнивай старую и новую систему на отдельных копиях одной исходной ревизии.
Используй 5–10 задач: малая правка, обычный баг, новая фича, смешанная API/UI задача,
изменение с риском данных, документация. Одни требования, одни проверки и окружение.

Записывай: итоговую корректность, пропущенные регрессии, вмешательства человека,
общее время, назначения ролей, раунды исправлений, входные/кешированные/выходные
и reasoning-токены, если они реально доступны. Не складывай родительские агрегаты
с уже включёнными в них дочерними значениями. Стоимость считай по своему тарифу;
токены, время и списание лимита подписки — разные величины.

Оставляй более дешёвый профиль только при сопоставимой полноте и корректности.
Без такого сравнения честный вывод — «устранены очевидные накладные расходы»,
а не «достигнут максимально эффективный режим».
