# Пересмотр правил разработки

Проверка выполнена 2026-11-14. Цель — переносимые инструкции Codex для обычной,
клиент-серверной и распределённой разработки без правил нумерации версий/сборок.
DataMatrixControl не изменён. Исходные пять файлов правил находятся в его
`.cursor/rules/`: использовано только их содержание, без механизма загрузки Cursor.

## Что перенесено и пересмотрено

| Исходное правило | Оценка | Что получилось |
|---|---|---|
| Строгие типы во всём коде | Полезно, но формулировка привязана к Python и может вызывать массовые несвязанные правки | Типы изменённых контрактов/структур по языку и действующим проверкам |
| Docstring у каждой функции/метода/класса | Избыточно для очевидных функций; расход контекста и шум | Документировать контракты, инварианты и нетривиальные решения |
| Clean code/SOLID | Слишком общо для исполнимого правила | Границы ответственности, минимальная область изменения, обоснованная абстракция |
| Unit-тесты критичных функций | Сохранено, но для распределённой системы недостаточно | Регрессии плюс проверки контрактов, БД, повторов и отказов по затронутой области |
| TODO с контекстом | Сохранено | Причина и задача/условие завершения |
| План перед любым кодом | Не оправдан для малых задач | Масштаб процесса уже выбирает dev-cycle; второй обязательный план не добавлен |
| Единый logger, отсутствие print | Реализация и исключения зависят от проекта | Принятый logger, CLI/stdout допустимы по назначению |
| ERROR/CRITICAL + traceback для исключений | Безусловное применение создаёт шум и дубли | Неожиданный сбой логируется на границе; ожидаемая валидация не требует traceback |
| DEBUG для протоколов и SQL | Уровень DEBUG сам по себе не защищает данные | Маскирование, ограничение объёма, запрет секретов на любом уровне |
| `truncate_text` до 2048 символов | Не соответствует найденной сигнатуре | Общий лимит объёма; в примере DMC указана семантика bytes |
| Ссылка на модуль логирования в коде и сборке | Не подтверждена в проверенной копии | Проверять фактические зависимости сборки |
| Всегда `venv`, только `requirements.txt` | Для DMC применимо частично, для всех проектов — нет | Проектный toolchain; manifest прямых зависимостей и принятый lock/constraints |
| Не записывать транзитивные зависимости | Разумно для некоторых manifest, неверно для lockfile | Разделены прямые и разрешённые зависимости; воспроизводимость сохраняется |
| Всегда `media`, PyInstaller/NSIS | Конкретная структура продукта | Использовать существующие каталоги и сборку |
| Не читать логи без необходимости | Сохранена адресность исследования | Диагностика по задаче, без сканирования архивов |
| Все изменения в CHANGES.LOG | Общий редактируемый файл конфликтует между ветками | После отдельного запроса пользователя введены обязательные отдельные записи; внутреннее фильтруется из пользовательской сводки |
| Docs только по ClientTypes, lowercase | Не переносимо и расходится с найденными именами | Документы по существующей структуре, аудитории и фактическому регистру путей |
| Любая правка ORM требует Alembic | Слишком широко: не каждая правка ORM меняет схему | Миграция при изменении физической схемы в принятом инструменте |
| Обязательные upgrade/downgrade | Недостаточно для безопасного изменения данных | Проверка перехода/чистого развёртывания; восстановление, без ложного обратимого downgrade |
| 15 циклов ревью, docs на каждый пункт, параллельный CHANGES.LOG | Уже пересмотрено в предыдущем этапе | Сохраняется существующий dev-cycle; второй механизм оркестрации не добавлен |
| VERSION, DB_VERSION, буквенные префиксы, bump по наличию плана | Исключено по запросу пользователя | Отдельное поле проектной политики без универсальных значений/алгоритма |

## Что подтверждено по текущим файлам DMC

Проверка относится к доступному рабочему каталогу, не ко всем веткам или установленным
сборкам. Отсутствующий файл означает, что правило нельзя исполнить по этому пути сейчас;
это не доказательство удаления функциональности во всём продукте.

- Утилита усечения текста считает байты UTF-8 и добавляет суффикс после усечения.
- Часть путей из прежних инструкций отсутствовала в проверенной копии.
- Наличие каталогов миграций не подтверждает рабочий процесс без исходников и команды запуска.
- Регистр имён каталогов документации следует сохранять при переносе.

## Чего недоставало для клиент-серверных систем

| Область | Добавленные требования | Когда читать |
|---|---|---|
| Контракты | Семантика полей/ошибок, ограничение запросов, совместимость потребителей, интеграционные проверки | Изменение API или сериализации |
| Сеть | Общий deadline, конечные retries с одним владельцем, неизвестный результат команды | Удалённые вызовы и reconnect |
| Доставка | Дубли, порядок, ack после устойчивого результата, согласование БД/публикации | Очереди и фоновые задачи |
| Состояние | Конкурентные изменения, транзакции, владельцы данных, кэш | БД и общий ресурс |
| Миграции | Смешанное развёртывание, блокировки, возобновляемый backfill, восстановление | Изменение схемы/данных |
| Доступ | Объектная/полевая авторизация, tenant isolation, SSRF, лимиты | Недоверенные входы и API |
| Эксплуатация | Корреляция, безопасная телеметрия, bounded labels, healthchecks, shutdown | Долгоживущие сервисы |
| Клиент | UI thread, гонки ответов, offline, неизвестное состояние команды, доступность | Web/desktop UI |

Это требования к поведению и проверке, а не требование внедрить все технологии.
Монолит с хорошими границами допустим. Не нужны Kafka, Kubernetes, service mesh,
CQRS, saga или outbox, если решаемая задача не требует их свойств. Если нужен
outbox/эквивалент, сначала ищем существующую реализацию и окно сбоя, которое закрываем.

## Как правила подключены

Первоначально в `AGENTS.md` добавлена таблица выбора семи тематических правил.
Последующее обязательное правило `history.md` описано в [истории изменений](change-history.md).
Каждый загружается по области задания. Никакой автоматический загрузчик по имени
каталога не предполагается: роли и навыки направлены читать `AGENTS.md`, оркестратор
передаёт пути правил, ревьюер проверяет достаточность выбора.

Пример: правка документа не требует чтения очередей, миграций и healthchecks.
Изменение сетевой команды с записью в БД требует контрактов, распределённого
выполнения, данных и безопасности в дополнение к инженерной базе.
Это дополнительные необходимые знания, поэтому суммарный размер комплекта вырос;
предыдущее сравнение «74% меньше» относится к набору до расширения правил.

Нумерация версий, префиксы, номера сборок и конкретный механизм версионирования
схемы не перенесены. Совместимость работающих клиентов, безопасные миграции и порядок
изменения схемы сохранены: это свойства корректности, а не алгоритм назначения версии.

## Уточнение длительных операций UI

Первоначальное правило клиента запрещало блокировать поток интерфейса и различало
загрузку/ошибку, но явно не требовало видимой обратной связи на всё время ожидания.
Теперь оно задаёт статус операции, честный прогресс, локальный индикатор или обоснованный
модальный экран, завершение busy при ошибке/отмене и проверку с медленным ответом.
Отдельный UI-агент и новый файл правил не нужны: это часть существующего `client.md`.

Анимация показывает состояние ожидания клиента, но не доказывает продвижение сервера.
Поэтому предусмотрены предел ожидания, неизвестный результат и проверка статуса,
а не обещание «просто подождите» при любом сбое. Фоновая служебная работа не требует
модального окна. Конкретные компоненты и временные пороги выбирает целевой проект.

Опора для выбора вида индикации — [Microsoft Progress controls](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/progress-controls):
различие определённого/неопределённого прогресса и возможность продолжать взаимодействие.
[WPF Threading model](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/threading-model)
объясняет короткие обработчики, фоновую работу и возврат обновлений в поток UI.
Это платформенные примеры; используемый API определяется фреймворком проекта.

## Источники проверки добавленных принципов

- Семантика безопасного повтора HTTP: [RFC 9110, §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2).
  Повтор неидемпотентной операции требует знания о её применении/безопасности повтора.
- Ограничение ожидания и усиления нагрузки повторами:
  [AWS Builders Library](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/).
- Различие publisher confirms и consumer acknowledgements:
  [RabbitMQ](https://www.rabbitmq.com/docs/confirms). Это пример конкретного брокера;
  детали гарантий выбранного транспорта нужно проверять отдельно.
- Объектная/полевая авторизация, стоимость запроса и SSRF:
  [OWASP API Security Top 10](https://api-security.owasp.org/editions/2023/en/0x11-t10/).
- Проверка блокировок DDL: [PostgreSQL ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html).
  Для другой СУБД используются её гарантии, а не скопированные команды PostgreSQL.
- Разделение сигналов готовности и перезапуска:
  [Kubernetes probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/).
- Риск утечки контекста через baggage:
  [OpenTelemetry](https://opentelemetry.io/docs/concepts/signals/baggage/).

Набор правил — инженерная адаптация этих принципов под workflow Codex, не сертификация
безопасности/надёжности и не обещание отсутствия дефектов.
