# Совместная проверка TDD, Git-workflow и UI

Проверка 2026-11-15: инструкции и маршруты на десяти сценариях, затем проверка
регистрации, ссылок, переносимости и инструментов истории. Это не измерение
токенов или качества разработки на реальном приложении.

## Исправленные источники лишней работы

| Проблема | Итоговое правило |
| --- | --- |
| Полный Git-workflow читался даже перед обычной правкой | Короткий baseline во входном навыке; операции с индексом, refs, интеграцией и публикацией — в условной ссылке |
| TDD мог заставлять повторять уже подтверждённый Red из CI | Подходящее доказательство для исходного кода, сценария, входов и зависимостей можно использовать; для исправленного состояния нужен Green |
| Проверенные тесты могли повторяться при передаче reviewer или оформлении commit | Результаты для того же состояния и условий переиспользуются; новые риски, изменения и требования проекта определяют дополнительные проверки |
| Ревью конкретного diff могло расшириться до всего рабочего дерева | Явные diff/пути/refs задают область; незакоммиченные изменения используются только при отсутствии явной области |
| Чистый merge мог восприниматься как отсутствие новых рисков | Всегда оценить объединённый результат; новые взаимодействия и решения требуют адресных проверок и ревью, смена SHA сама по себе — нет |
| Визуальная правка могла запускать незатронутые сетевые сценарии | Проверки медленного ответа, отмены и гонок выбираются по эффекту; визуальное изменение проверяется рендером и затронутым взаимодействием |
| Текстовая концепция могла требовать запуска приложения или файла плана | Явный read-only/ответ словами выполняется без записи, истории и рендера; исполняемый прототип проверяется как реализованный UI |
| Небольшой пробел в готовом UI мог запускать designer заново | Автор использует существующие паттерны и фиксирует допущение; существенное противоречие передаёт оркестратору |
| Лимит авторов и общие ресурсы трактовались неоднозначно | Максимум два пишущих исполнителя, включая основную сессию; области записи не пересекаются, конфликтующие проверки изолируются или идут последовательно |

## Минимальные маршруты

| Задача | Исполнение и проверка |
| --- | --- |
| Опечатка в документации | Основная сессия, подходящая проверка, запись истории; без субагентов |
| Backend-баг с подходящим CI Red | Основная сессия или developer, Green и один reviewer; без повторного Red |
| Локальный UI-баг по готовому решению | Основная сессия или ui_developer, проверки поведения и reviewer; без designer |
| Значимая визуальная переработка по готовому макету | ui_developer и reviewer; без designer и искусственного Red |
| Новый UI и API | planner только для существенной декомпозиции, designer только при нехватке дизайна; ui_developer и основной/backend-автор в пределах лимита, проверка интеграции и один reviewer |
| Концепция только текстом | designer либо основная сессия при недоступности роли; без Git-изменений, истории, TDD и запуска приложения |
| Чистый рефакторинг | Зелёный baseline и результат после; characterization-тесты при пробелах, независимое ревью по риску |
| Ревью переданного чужого diff | Проверка явной области; второй reviewer только по риску/запросу, без записи и истории |
| Commit уже проверенного пакета | Основная сессия проверяет точный состав и сохранность чужого staged; без нового цикла исключительно из-за оформления commit |
| Интеграция после PASS | Проверка объединённого результата; адресные тесты/ревью для непроверенных взаимодействий, история для нового логического результата |

Каждый законченный результат с изменением файлов получает запись истории по общему
правилу; передача между ролями, повторное ревью и оформление commit не дублируют её.

Explorer, planner, documenter и expert не являются обязательными ступенями.
Исправления и follow-up получает прежний автор/reviewer. Отдельные Git-, TDD- и
UI-reviewer роли не добавлены. Общий reviewer проверяет стабильный интегрированный
результат; изменение поведения, высокий риск и значимый UI сохраняют обязательное ревью.

Короткие указания роли прочитать применимые правила, соблюдать область записи
и не делегировать дальше сохранены: они нужны при запуске без истории родителя.
Предметные требования остаются в тематических правилах, а подробности маршрутов
читаются по необходимости. Восемь профилей моделей/effort не изменены.
