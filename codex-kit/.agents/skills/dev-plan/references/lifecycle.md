# Жизненный цикл плана

Одна связанная цель — один файл `.plans/YYYY-MM-DD-slug.md`. Путь постоянный,
состояние хранится внутри файла. Существующий формат сохраняется. Новые планы
используют [шаблон](plan-template.md) с `plan_format: 1`.

## Состояния плана

| Статус | Значение |
| --- | --- |
| draft | Проработка цели и подхода |
| ready | Критерии определены и хотя бы одна задача доступна для начала |
| in_progress | Выполнение началось, есть доступная работа |
| blocked | Продолжение требует внешнего условия, доступные работы исчерпаны |
| paused | Пользователь явно отложил работу |
| completed | Выполнены критерии, проверки, обязательное ревью, документация и история |
| cancelled | Пользователь отменил план или согласовал замену |

Перед ready автор применяет [проверку простоты](../SKILL.md#проверка-простоты).
Обычный путь — draft → ready → in_progress → completed. Уже порученную реализацию
продолжай после подготовки плана, дополнительного согласования ready не требуется.
Из in_progress переходи в blocked по факту препятствия и обратно после его устранения.
paused сохраняется до запроса пользователя продолжить. После возобновления выбери
in_progress или blocked по доступности работы. Возврат ready в draft допустим при
пересмотре ещё не начатой задачи. При изменении объёма начатого плана примени
[проверку простоты](../SKILL.md#проверка-простоты) к затронутым оставшимся задачам на месте.
Любой незавершённый план может быть отменён по указанному выше основанию.
completed переоткрывается при обнаруженном невыполненном критерии, с причиной.
Новая цель получает новый план. Для возобновления cancelled нужен запрос пользователя.

## Задачи и зависимости

Каждая задача — проверяемый результат с постоянным ID T01, T02 и далее. При вставке
задач сохраняй прежние ID. Заголовок имеет вид `### T01 — Название`.
Состояние задаёт поле `Статус`, зависимости — `Зависимости: T01, T02` или `нет`.
Область, критерии, команды проверок и необходимость ревью описываются по существу задачи.

Переходы задач — todo → in_progress → review → done. Если независимое ревью по
dev-cycle не требуется, после проверок допустим прямой переход in_progress → done.
Замечания возвращают review в in_progress. Препятствие переводит задачу в blocked,
с полями `Блокер` и `Разблокировка`. После снятия продолжай с нужного этапа.
Для cancelled укажи `Причина`. Пересмотри активные зависимости от отменённой задачи.

Начинай зависимую задачу после done её предшественников. Для параллельной работы
клиента и сервера укажи существующий контракт. Если стороны зависят от его изменения,
выдели согласование нового контракта в предварительный результат.
Условия владения файлами и ресурсами определяет dev-cycle.
done требует поля `Результат` с краткими фактами проверок и обязательного ревью
(или его неприменимости). Несколько задач могут ссылаться на одно общее ревью.
Если ревью входит в критерии задачи, до него сохраняй review.

## Прогресс и возобновление

Прогресс равен числу done среди всех задач, кроме cancelled. Показывай количества
по состояниям и, при необходимости, процент закрытых задач. При нулевом объёме
процент отсутствует. Добавление и переоткрытие задач меняет прогресс.
Фазы служат группировкой описания, собственные статусы и проценты им не требуются.

Основная сессия обновляет файл после результата, смены состояния или блокировки.
Она сохраняет дату `updated`, следующий шаг, а для blocked плана — общую причину
и условие снятия. Для paused/cancelled плана в `## Текущее состояние` нужна `Причина`.
Блокировка одной задачи допускает работу над другими. Если они доступны, план остаётся
in_progress. При паузе сохраняй состояния задач как точку продолжения.

При возобновлении сверяй done (в старом формате `[x]`) с текущим состоянием и
доказательствами проверок. Переиспользуй актуальные результаты. Расхождения проверяй
адресно, переоткрывай затронутые задачи и пересматривай их зависимые результаты.
Субагент получает назначенные задачи и возвращает результат основному агенту.
Правила записи истории остаются в history.md, обновление прогресса вместе с результатом
использует его запись. Отдельное законченное изменение только плана получает внутреннюю запись.

## Проверка

Проверку запускает агент, записавший план — planner при создании или основная сессия
при выполнении. После связанного набора правок он сам выполняет одну команду из корня
целевого проекта. Пользователь запускает обычные dev-plan/dev-cycle.
Перед возобновлением также проверь файл, если для этой версии нет успешного результата.
Успешную проверку той же версии файла тем же скриптом переиспользуй при передаче работы.

```powershell
python .codex/scripts/plans.py .plans/YYYY-MM-DD-slug.md
```

Для машинного вывода добавь `--json` к тому же запуску. При коде 1 исправь ошибки
структуры или состояния по фактам и повтори проверку. Критерии готовности и зависимости
сохраняй обоснованными. Код 2 с `unsupported` означает проверку старого формата самим
агентом. При ошибке чтения/запуска исправь путь или окружение, а если это невозможно,
явно сообщи ограничение. Завершение плана формата 1 подтверждай после успешной проверки
его итогового состояния. В ответе достаточно краткого результата и значимых ошибок.

На стадиях draft и ready `warnings` указывают задачи с одинаковым названием.
При разработке плана автор сверяет их результаты и при необходимости объединяет или уточняет задачи.
Подсказки сохраняют код выхода и не требуют подтверждения пользователя.

Скрипт читает один файл и проверяет снимок состояния. Он проверяет даты, ID, статусы,
зависимости, циклы, обязательные сведения о блокировке/результате и согласованность
статуса плана. `ready` в JSON перечисляет todo с выполненными зависимостями, даже
если план paused или cancelled. Разрешение продолжать задаёт статус и запрос пользователя.
Коды выхода — 0 для корректного формата 1, 1 для ошибок, 2 для старого/неподдерживаемого
формата или ошибки чтения. Старые планы агент проверяет по существующему формату.

Машинные поля пишутся отдельной строкой с начала строки, без Markdown-выделения.
Метаданные однострочные, даты в YYYY-MM-DD, статусы и plan_format без кавычек.
Примеры внутри fenced code blocks и HTML-комментариев пропускаются.
Человеческая проверка подтверждает правдивость результатов, полноту критериев и
основания переходов. Скрипт не имеет истории состояний и не подтверждает факт тестов.
