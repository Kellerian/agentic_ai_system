# История из отдельных записей

Один законченный логический результат — один файл в `entries/YYYY/`.
Каталог создаётся при первой записи. Исходные записи хранятся в Git вместе с кодом,
не удаляются сборщиком и не имеют общего редактируемого индекса.

## Создать запись

Из корня целевого проекта (Python 3.11+, без сторонних пакетов):

```powershell
python .codex/scripts/changes.py new --kind fixed --component "Печать" --user "Устранена повторная печать после кратковременного разрыва связи." --support "После потери ответа команда могла отправляться повторно. Добавлена сверка статуса. Регрессионный тест пройден." --ref "TASK-123" --ref ".plans/printing.md"
```

Для внутренних изменений:

```powershell
python .codex/scripts/changes.py new --kind internal --component "Тесты" --internal-reason "Поведение продукта не меняется." --support "Убрана зависимость теста от системного времени; проверены оба граничных случая."
```

Имя содержит UTC-время с микросекундами и UUID4, например
`20261114T120000123456Z_765c5c85-f2c0-4be1-bd4e-5156a6a3f831.json`.
Время удобно для человека и сортировки; уникальность обеспечивает UUID и эксклюзивное
создание файла. Оно не используется для определения принадлежности к выпуску.
Запись публикуется после полной сериализации атомарно в той же файловой системе:
Windows — переименованием без перезаписи, POSIX — созданием hard link без перезаписи.
Если файловая система не поддерживает этот механизм, команда завершится ошибкой,
не оставив частичный JSON. Временные файлы не попадают в историю.

## Формат JSON

Это иллюстрация, не готовая запись о реально выполненной задаче:

```json
{
  "schema_version": 1,
  "id": "765c5c85-f2c0-4be1-bd4e-5156a6a3f831",
  "created_at": "2026-11-14T12:00:00.123456Z",
  "kind": "fixed",
  "component": "Печать",
  "user": "Устранена повторная печать после разрыва связи.",
  "support": "Условия проявления, исправление, выполненные проверки и ограничения.",
  "internal_reason": null,
  "breaking": false,
  "action_required": null,
  "references": ["TASK-123", ".plans/printing.md"]
}
```

- `kind`: `added`, `changed`, `fixed`, `removed`, `security`, `docs`, `internal`.
- `component`: понятная функциональная область; попадает в обе аудитории.
- `user`: текст для пользователя или `null`. Во втором случае обязателен `internal_reason`.
- `support`: обязательный технический текст, не попадает в пользовательский журнал.
- `breaking`: несовместимость; при `true` обязательны `user` и `action_required`.
- `action_required`: действие при обновлении, если нужно. Это текст для обеих аудиторий.
- `references`: ссылки/идентификаторы; выводятся только для поддержки.
- `schema_version` описывает формат записи, не версию приложения; задаётся инструментом.

Текст — обычный текст. Сборщик экранирует разметку; HTML, изображения и исполняемые
вставки не поддерживаются. Никаких секретов/персональных данных в истории.
Схему проверяет `changes.py check`, в том числе имя файла, ID, время и неизвестные поля.

## Проверить и увидеть черновик

```powershell
python .codex/scripts/changes.py check
python .codex/scripts/changes.py preview --all --release "Предпросмотр" --date 2026-11-14 --output build/notes-preview
```

`check` без базы читает рабочие файлы, включая незакоммиченные. `preview` тоже читает
рабочее дерево и помечает результаты как черновик. Вместо `--all` у preview можно
указать `--base <предыдущая-ревизия>` для исключения записей из базового снимка.
Вывод требует новой папки; существующие файлы не перезаписываются.

## Сборка журнала выпуска

```powershell
python .codex/scripts/changes.py build --base <предыдущий-тег> --head <коммит-сборки> --release <название-выпуска> --date <YYYY-MM-DD> --output <новая-папка-артефакта>
```

Первый выпуск этой истории или намеренная полная сводка: `--all` вместо `--base`.
Остальные параметры остаются теми же. Уголковые скобки в примере нужно заменить.
Git refs должны быть доступны локально; shallow checkout иногда требует получить базу.
`--base` должен быть предком `--head` и соответствовать предыдущему выпуску именно
этой линии поддержки. Для prerelease→final выбирай базу согласно желаемой полноте заметок.

Создаются:

- `CHANGELOG.md` — только пользовательские изменения;
- `SUPPORT-CHANGELOG.md` — все записи, условия, ссылки и стабильные ID;
- `manifest.json` — label/date, точные Git-коммиты и ID/хеши выбранных записей.

Сборщик читает **Git-снимки**, а не текущие файлы и не сообщения коммитов. Выбирает
записи, ID которых есть в `head`, но нет в `base`. Поздно слитая старая ветка не
теряется из-за даты записи. Backport переносит тот же ID; в каждой линии он входит
в тот выпуск, в котором впервые появляется относительно её базы.
При изменении/удалении записи из базовой истории сборка завершается ошибкой.

Одинаковые снимки, label и date дают одинаковые байты отчётов и manifest.
Повторная сборка намеренно выбирает те же записи, а не «потребляет» их.
Собирай программный артефакт из того же `source_commit`; инструмент не проверяет
содержимое exe/контейнера. В dirty checkout commit-based журнал не включает новые
файлы — это не выпуск незакоммиченных изменений. Одна пара base/head описывает одну
линию выпуска; оркестрация независимых пакетов monorepo остаётся задачей сборки.

Не сохраняй общий производный changelog в каждой feature-ветке. В пользовательский
дистрибутив включай `CHANGELOG.md`. Технический отчёт и manifest храни в артефактах CI
и передавай поддержке по принятому каналу; не упаковывай весь output автоматически.
Если технический журнал должен быть публичным, это отдельная политика проекта.
Manifest создаётся последним;
не используй вывод команды с ненулевым exit code. Формат/номер приложения не меняется.

## Проверка перед слиянием

```powershell
python .codex/scripts/changes.py check --base <база-PR> --head HEAD --require-entry
```

Команда проверяет неизменность старых записей и требует минимум одну новую, если
изменились файлы вне `.changes/entries/`. Проверка консервативна: даже правка плана/тестов
требует короткой внутренней записи. Она не доказывает полноту текста или соответствие
каждой записи коду — это проверяет ревью. Все сравниваемые изменения должны быть
закоммичены. Для локальной работы используй простой `check` и критерий завершения.

Закрытие плана вместе с оформленными результатами не требует дублирующей записи.
Если отдельный PR только меняет статус уже реализованного плана, добавь внутреннюю
запись об обновлении плана со ссылками на прежние результаты: это новый служебный
результат, а не повторное объявление реализованной функции. Исключения из CI нет.

До слияния уточняй свою запись вместо создания дублей за каждую попытку исправления.
Если до слияния изменение полностью отменено, его ещё не принятое описание можно убрать.
После принятия истории отмену оформляй отдельной записью; сборщик не выводит автоматически
«итоговую семантику» цепочки feature/revert. Редакторская проверка выпуска всё ещё нужна.

При переходе с прежнего журнала сохрани его как исторический архив. Начни fragment-
историю с выбранной базовой ревизии; автоматического импорта старых заметок нет.
