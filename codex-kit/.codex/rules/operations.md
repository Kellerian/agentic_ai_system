# Эксплуатация и диагностика

Применяется к логам, метрикам, запуску сервисов, конфигурации и healthchecks.

- Используй существующий logger/структурированные события. Прикладной `print`
  не заменяет логирование сервиса; stdout как транспорт логов контейнера и вывод
  CLI допустимы. Не навязывай конкретный logger или путь каталога.
- Логируй результат операции, длительность, код ошибки и безопасный correlation ID.
  Stack trace — для неожиданных исключений на границе обработки, без многократного
  log-and-rethrow по всем слоям. Ожидаемый отказ валидации не требует ERROR+traceback.
- Не записывай сырые тела/SQL-параметры, токены и персональные данные. Маскирование
  и ограничение объёма действуют на всех уровнях, включая DEBUG. Trace/baggage
  переносит только разрешённый контекст; входные идентификаторы ограничены и проверены.
- Для критичного нового поведения определи, как заметить отказ/задержку/очередь.
  Переиспользуй метрики проекта; labels имеют ограниченную кардинальность,
  user/request IDs остаются в допустимых логах/traces, не в labels метрик.
- Startup отвечает за завершение инициализации; readiness — за приём новой работы;
  liveness — за необходимость перезапуска процесса. Отказ внешней зависимости сам
  по себе не повод перезапускать здоровый процесс. Зависимости readiness определяй
  по возможности обслуживания запроса, чтобы частичный сбой не снимал без причины
  всю систему. Проверки состояния имеют ограниченный срок и стоимость.
- Остановка прекращает приём работы, ограниченно дожидается текущей и освобождает
  соединения/consumer. Незавершённое сообщение не подтверждается как выполненное;
  повтор после перезапуска должен быть безопасен.
- Конфигурация имеет документированные defaults/единицы, валидируется до приёма
  работы; некорректный обязательный параметр не подменяется тихим fallback.
  Не меняй environment/секреты через исходный код.
- Изменение сборки/запуска проверь в целевой форме артефакта по риску: контейнер,
  desktop bundle или исполняемый файл. Работоспособность из IDE не подтверждает
  упакованный результат. Обнови операционные инструкции, когда меняется обслуживание.
- При изменении развёртывания, схемы или совместимости зафиксируй порядок обновления
  компонентов, проверку после установки и сигнал остановки выпуска. Проверь, может ли
  прежнее приложение работать с новой схемой/уже записанными данными. Если нет, нужен
  план исправления вперёд либо проверенного восстановления с учётом новых записей;
  откат бинарника не равен откату данных. Проверь восстановленный сценарий на стенде.
  Используй существующий runbook; это не разрешение на production-действия.
