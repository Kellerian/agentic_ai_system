# Инженерная база

- Найди действующие точки входа, паттерны и команды проекта; устаревшие инструкции
  не доказывают наличие реализации. Расхождения указывай.
- Используй toolchain/окружение из manifest, CI или project.md; не угадывай venv
  и не меняй глобальное окружение. Для Python — проектный интерпретатор и `python -m pip`;
  для автономной stdlib-утилиты допустим доступный совместимый Python.
- Прямые зависимости — в manifest, разрешённые — в lock/constraints. Не вычищай
  транзитивные записи и не обновляй всё дерево ради одного пакета. Generated-файлы
  обновляй их инструментом, не вручную.
- Сохраняй границы модулей, типы интерфейсов и паттерны проекта. Абстракция/сервис
  нужны для конкретной ответственности. Комментарий объясняет инвариант или решение.
- Освобождай ресурсы, обрабатывай ошибки на подходящей границе, не скрывай отказ
  под успехом. TODO содержит причину и условие завершения/задачу.
- Для воспроизводимого бага и нового/изменённого автоматически проверяемого поведения
  применяй TDD небольшими шагами: выбери сценарий из критериев, возьми подходящий тест
  или напиши новый до реализации. Подтверди ожидаемое падение на исходном поведении (Red),
  реализуй поведение (Green), при необходимости упрости код/тесты с повторной проверкой (Refactor).
  Red можно подтвердить доступным результатом CI для тех же исходного кода, сценария,
  входов и зависимостей с нужной причиной падения; иначе запусти тест до изменения.
  Поломка окружения не подтверждает Red. Если тест уже зелёный, выясни, ловит ли он
  требуемое отличие; не создавай искусственное падение и не утверждай, что баг воспроизведён.
- Ожидаемый результат теста выводи из требований/контракта, не из написанной реализации.
  Проверяй наблюдаемый результат и значимые границы, а не частные методы или число строк.
  Не ослабляй assertions и не подставляй ответы примеров ради Green. Изменение неверного
  теста обоснуй контрактом. Отдельного агента, коммита и полного прогона на каждый Red не нужно.
- Для чистого рефакторинга сначала получи/проверь зелёный baseline; при пробеле добавь
  characterization-тест текущего допустимого поведения. Искусственный Red не требуется.
  Для docs/косметики без изменения поведения тесты не создавай ради TDD. Визуальный
  эксперимент/исследование или недоступная среда требуют конкретной причины отклонения
  и подходящей альтернативной проверки; готовый код не выдавай за прошедший test-first.
- Выбирай минимальный уровень теста, доказывающий сценарий. Для изменённых API, БД,
  очередей и миграций проверяй реальные границы на изолированной среде: mocks не
  доказывают SQL/сериализацию/доставку. UI-логику проверяй поведением, внешний вид —
  дополнительно рендером по правилам клиента. Управляй временем/состоянием детерминированно.
  Для применимого TDD укажи тест/команду, фактические Red/Green либо конкретное отступление.
  Вне этой области достаточно релевантной проверки, без формального отчёта о пропуске TDD.
  Недоступные обязательные проверки остаются открытыми; TDD не заменяет интеграцию/ревью.
- Выполняй проверки затронутой области, включая обязательные в этом случае команды CI.
  После изменения нужен результат для нового состояния. Подтверждённый запуск для
  того же кода/сценария/условий можно переиспользовать без повтора, если нет нового риска
  или требования проекта. Расширяй проверки по изменённым зависимостям, недоступное указывай.
- Обновляй затронутые контракты, настройки и инструкции в существующей структуре
  docs/assets, сохраняя регистр путей. Косметике не нужна новая статья.
  Тестовые результаты не выдавай за production-наблюдения.
