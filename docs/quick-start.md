# Перенос комплекта в другой проект

## 1. Скопировать

Из каталога `codex-kit/` перенеси в **корень целевого проекта**, сохраняя структуру
и скрытые папки:

| Что | Назначение |
| --- | --- |
| `AGENTS.md` | Выбор процесса и применимых правил |
| `.codex/` целиком | Конфигурация, восемь ролей, правила, контекст и скрипты |
| `.agents/skills/` целиком, включая `references/` | Пять навыков и условно читаемые инструкции |
| `.changes/README.md` | Формат истории; `entries/` создастся при первой записи |

Совпадающие файлы объединяй по diff, сохраняя настройки проекта и заполненный
`project.md`. Не заменяй существующий config целиком и не создавай повторные TOML-секции.
Согласуй вложенные `AGENTS.md` и прежние маршруты агентов, чтобы не осталось двух циклов.
Корневые `docs/`, `tests/`, `examples/` и `.changes/entries/` **этого репозитория**
для работы комплекта не нужны; его историю в новый проект не переноси.

## 2. Настроить под проект

Заполни `.codex/project.md` проверенными фактами, обычно достаточно 20–50 строк:

- Стек, точки входа, границы клиента/сервера и критические инварианты.
- Окружение, рабочие каталоги и точные команды быстрых тестов, интеграции и сборки.
- API/события, миграции, тестовая БД, таймауты, права и развёртывание — по применимости.
- Для UI: стиль/компоненты, запуск, тестовые данные и способ визуальной проверки.
- Бюджеты производительности, пути документации и параметры сборки журнала выпуска.

Модель и `model_reasoning_effort` каждой роли меняются в `.codex/agents/kit_*.toml`.
Начни с готовых профилей; недоступные модели замени явно на поддерживаемые в своей среде.
Комплект не меняет модель основной сессии. Политику версионирования задай отдельно.
Секреты в инструкции не записывай.

## 3. Проверить файлы

Из корня целевого проекта, Python 3.11+ без дополнительных пакетов:

```powershell
python .codex/scripts/validate_kit.py
python .codex/scripts/changes.py check
```

В командах заполненного `.codex/project.md` допустимы абсолютные пути к локальным инструментам.
Для ссылок на файлы проекта используй относительные пути.

Ожидается `PASS`; до первой записи `PASS: 0 entries` нормален. При наличии локального
кеша моделей можно дополнительно выполнить в PowerShell:

```powershell
python .codex/scripts/validate_kit.py --models-cache "$env:USERPROFILE/.codex/models_cache.json"
```

Валидатор проверяет файлы ролей, уникальность их имён и ссылки. Кеш показывает
совместимость профиля с локальным каталогом. Доступность запуска проверяется в новом чате.
При обновлении прежней копии можно убрать восемь секций `[agents.kit_*]`, которые
указывали на те же файлы. Собственные роли и настройки целевого проекта сохрани.

## 4. Проверить в Codex

Открой целевой проект и новый чат. Для проектного `.codex/config.toml` требуется
доверие к проекту; проверь предупреждения загрузки конфигурации.
Это условие описано в [документации Codex](https://learn.chatgpt.com/docs/config-file/config-basic).

Отправь один проверочный запрос:

```text
Проверь установку комплекта без изменения файлов и Git-состояния.
Прочитай AGENTS.md и .codex/project.md. Назови применимые правила и минимальный
маршрут для: опечатки в docs; бага поведения; нового UI по готовому макету.
Затем запусти только kit_explorer по runtime-инструкции комплекта с профилем
из его TOML: найди одну реальную точку входа и соответствующую команду проверки.
Дождись результата. Укажи способ запуска и переданные модель/effort;
отдели подтверждённые параметры от того, что инструмент не позволяет проверить.
Если делегирование недоступно, сообщи об этом, не имитируй запуск.
```

Ожидается один реальный субагент с конкретными путями/командой и такие маршруты:
опечатка — основная сессия; баг — автор с применимым TDD и независимый reviewer;
значимый UI по достаточному макету — ui_developer и reviewer, без designer.
Правила читаются выборочно через `AGENTS.md`: сама папка `.codex/rules/` их не активирует.

Если запуск не работает, проверь путь проекта, конфигурацию, доступность модели
и инструмента делегирования. Поддержанные варианты запуска описаны в
[runtime.md](../codex-kit/.agents/skills/dev-cycle/references/runtime.md)
(после копирования — `.agents/skills/dev-cycle/references/runtime.md`).
Запуск одной роли подтверждает только этот маршрут и профиль; остальные проверяются
при первом использовании, без обязательного запуска всех восьми ради установки.

## 5. Начать работу

«Составь план» сохраняет план в `.plans/YYYY-MM-DD-slug.md`. В ответе агент укажет
путь и результат проверки. «Покажи план в чате» возвращает сам план без создания файла.
До выдачи автор объединяет шаги одного результата и проверяет, оправданы ли новые компоненты.
В локальном Codex открой сессию из корня целевого проекта. При объединении
`.codex/hooks.json` сохрани существующие обработчики. В интерфейсе `/hooks` проверь
и одобри проектный `PostToolUse` после просмотра определения и обоих Python-скриптов.
После `apply_patch` по файлу в `.plans/` агент получит статус и отпечаток успешной проверки.
Для этой версии повторный запуск не нужен. Если результат отсутствует, в том числе при
записи через shell или при отключённом хуке, агент сам
выполнит `python .codex/scripts/plans.py .plans/имя-плана.md` из корня проекта.
[Настройка хуков Codex](https://learn.chatgpt.com/docs/hooks). Формат и переходы описаны в
[жизненном цикле планов](../codex-kit/.agents/skills/dev-plan/references/lifecycle.md).

Первая небольшая реальная задача: `$dev-cycle Исправь … Критерии готовности: …`.
Проверь фактические тесты, независимое ревью при изменении поведения, визуальные
свидетельства для UI и одну запись результата в `.changes/entries/`.
Read-only проверка установки записи не требует; сам перенос файлов — требует.

Чтобы история контролировалась автоматически, подключи к CI `changes.py check`
с `--base`, `--head` и `--require-entry`, а к сборке — `changes.py build` из коммита
артефакта. Копирование файлов само по себе CI не настраивает. Команды, выбор базы
и состав поставки — в [руководстве истории](../codex-kit/.changes/README.md)
(в целевом проекте — `.changes/README.md`).

В этом репозитории проверки уже подключены для PR и push в main. При переносе команды
тестов и пути к скриптам зависят от целевого проекта. [Пример для GitHub Actions](../.github/workflows/kit.yml)
