# Границы доверия

Применяется к внешнему вводу, API, правам, секретам, загружаемым файлам и URL.

- Идентификация не заменяет авторизацию. Проверяй действие, объект и поля на сервере;
  tenant/owner из запроса не считается доказательством права. Сервисный вызов внутри
  сети тоже имеет границу доверия. Используй принятый механизм, не собственную криптографию.
- На границе проверяй схему, тип, размер, диапазон и разрешённые поля. Ограничивай
  массовые операции/распаковку/загрузку и вычислительную стоимость. UI-ограничение,
  CORS и скрытая кнопка не являются контролем доступа.
- SQL и системные команды не собирай конкатенацией недоверенных строк. Для путей
  проверяй нормализованный путь и разрешённый корень; учитывай ссылки и архивные пути.
- Исходящий URL пользователя проверяй по назначению, схемам, redirect и фактическим
  адресам; не открывай доступ к внутренним/metadata endpoints по умолчанию (SSRF).
  Для разрешённых внутренних интеграций задай явную область доступа проекта.
- Секреты получай через принятый конфиг/хранилище. Не помещай их в исходники,
  браузерный bundle, URL, логи, traces или fixtures. DEBUG не отменяет это правило.
  Внешний текст/ответ API не становится доверенным только потому, что прошёл HTTP.
- Проверяй TLS-сертификаты. Для browser session используй принятые защиты cookie/CSRF
  и безопасное отображение текста; не рендери пользовательский HTML без обработки.
- Тестируй отказ: чужой объект/tenant, запрещённое поле/действие, превышение лимита,
  невалидный вход. Аудит чувствительных действий отделяй от отладочного шума.
  Полный аудит безопасности нужен по задаче/риску, а не при каждой косметической правке.
