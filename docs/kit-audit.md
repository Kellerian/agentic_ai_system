# Итоговый аудит комплекта

Дата: 2026-11-14. Проверены переносимые AGENTS, четыре навыка, шесть ролей,
регистрация, девять тематических правил, инструменты истории/валидации, тесты
и согласованность сопровождающих документов. DataMatrixControl не изменялся.

## Исправленные проблемы

| Наблюдение | Изменение |
|---|---|
| Ревью происходило до итоговой интеграции и крупных docs/config | Сначала стабилизируются реализация, интеграция, проверки, документы и текст истории; затем одно ревью. Существенные последующие изменения требуют адресного follow-up |
| `completed` описывался раньше создания истории | История сохраняется/проверяется до закрытия плана |
| Dirty baseline мог не учитывать индекс и новые файлы | Отдельно фиксируются staged/unstaged и исходное содержимое новых файлов; итог сравнивается с baseline |
| Общий контракт согласован, но нет владельца schema/codegen | Один владелец общих файлов, одна ревизия контракта для обеих сторон и явный владелец интеграции |
| Отдельный review чужого diff всегда запускал субагента | Независимая от автора основная сессия может выполнить его сама; обязательный reviewer при реализации поведения сохранён |
| Маршруты основной сессии могли восприниматься как новый цикл субагента | В AGENTS явно разделены оркестрация и назначенная подзадача |
| Отдельное закрытие уже выполненного плана конфликтовало с CI истории | Для самостоятельного изменения плана нужна внутренняя запись; закрытие в составе той же реализации не дублирует её |
| Повторялись инструкции истории, предметные списки в ролях и подробные формулировки правил | Семантика истории сосредоточена в history.md; роли выбирают предметные проверки через AGENTS; сокращены engineering/client/performance/dev-cycle |
| Валидатор падал на массиве вместо строки model/effort | Сначала проверяются типы обязательных полей, возвращается диагностическая ошибка; добавлен регрессионный тест |

Сохранены полезные краткие напоминания: субагент не получает весь контекст родителя,
поэтому ему нужны указание прочитать проектные правила, границы записи и запрет
самостоятельного делегирования. Удаление любого повтора ради числа символов ухудшило
бы переносимость. Профили моделей/effort и критерии независимого ревью не ослаблены.

## Что дополнено для клиент-серверной разработки

- Контракты явно охватывают события, общий codegen и проверку реальных сторон вместе.
- Поздний ответ старой сессии не возвращает данные в UI после logout/смены пользователя.
- Для изменения развёртывания/схемы/совместимости требуется порядок обновления,
  сигнал остановки и проверяемое восстановление. Откат старого приложения должен
  учитывать новую схему и новые записи; при несовместимости нужен другой путь восстановления.
- Маршрут эксплуатации срабатывает и для критичного нового поведения, а не только
  при редактировании уже существующих логов/healthchecks.

Условное правило восстановления опирается на
[Microsoft: Safe deployment practices](https://learn.microsoft.com/en-us/azure/well-architected/operational-excellence/safe-deployments):
при ухудшении состояния развёртывание останавливают, а rollback/roll-forward данных
нуждается в отдельном плане. Azure, canary, feature flags и новая инфраструктура
не становятся обязательными зависимостями комплекта. Правила нумерации версий не добавлены.

## Объём и чтение контекста

Сравнение до/после этого аудита: одинаковые 24 файла Markdown/TOML инструкций
и конфигурации внутри `codex-kit`, включая проектный шаблон. UTF-8 декодирован,
переводы строк нормализованы при чтении Python. Исключены скрипты, тесты,
руководство `.changes/README.md`, примеры, отчёты и история этого репозитория.

| Набор | До, символов | После, символов |
|---|---:|---:|
| Все инструкции/конфигурация | 47 109 | 43 710 |
| Минимум для малой docs-правки: AGENTS + project + engineering + history + dev-docs | 11 007 | 10 019 |
| Основа цикла: AGENTS + project + engineering + history + dev-cycle | 15 274 | 12 761 |

Общий объём уменьшен на **7,2%**, основа цикла — примерно на **16,5%**, несмотря
на новые ограничения. Предметные правила, роли и runtime добавляются по необходимости;
это не полный расход конкретного задания и не измерение токенов/стоимости.

AGENTS теперь запрещает рекурсивное чтение всех ссылок и ненужное повторное чтение
уже доступного текста. Исходники служебных скриптов и полное руководство истории
не нужны для обычного вызова команды. Read-only исследование не создаёт историю;
неназначенный субагент передаёт факты владельцу вместо самостоятельной записи.

## Что остаётся проектным

| Что ещё нужно для работы | Где задать |
|---|---|
| Рабочий toolchain, подготовка окружения, команды быстрых и обязательных проверок | `.codex/project.md`, существующие manifest/CI |
| Источник API/событийных схем, поддерживаемые потребители, владелец данных | project.md и существующие схемы |
| Интеграционный стенд, реалистичные fixtures, проверка клиент → сервер → БД/очередь | Тесты проекта; разрешённые окружения |
| Численные бюджеты производительности, таймауты, лимиты, UI-компоненты индикации | Проектные требования и измерения |
| Порядок обновления, наблюдаемые критерии остановки и восстановление | Существующий runbook и проверка на стенде |
| Обязательный контроль истории и сборка заметок вместе с артефактом | Вызовы changes.py в реальном CI/build script |

Отсутствие этих фактов нельзя компенсировать ещё десятью общими правилами.
Не добавлены обязательные новые агенты, ADR на каждую правку, полный security-аудит,
нагрузочный прогон для косметики или определённый брокер/СУБД/оркестратор.

## Проверка и пределы вывода

Валидатор с локальным кешем моделей и все четыре навыка проходят структурную проверку.
30 автоматических тестов проходят: 21 для истории, 9 для комплекта. Новый тест
сначала воспроизвёл TypeError для model/effort, затем прошёл после исправления.
Независимый reviewer исследовал шесть сценариев; найденные проблемы учтены выше.
Финальный статус повторного ревью фиксируется в [журнале проверок](validation.md).

Это статический и сценарный аудит, а не доказательство отсутствия любых дефектов.
Нативная загрузка ролей в другом клиенте, реальные client/server проверки и скорость
DMC здесь не проверялись. Для выбора наиболее выгодных моделей нужен сопоставимый
прогон реальных задач и телеметрия, как описано в [разборе эффективности](efficiency-review.md).
