# Цикл разработки

Работай в целевом репозитории по `AGENTS.md`, `.codex/project.md` и выбранным правилам.
Навык разрешает необходимое делегирование; оркестрирует только основная сессия.

## Масштаб

- Малое локальное изменение без изменения поведения и с низким риском: основная
  сессия, подходящая проверка и история. Без отдельного плана и агентов.
- Изменение поведения или высокий риск (данные, права, конкурентность, миграции,
  протоколы устройств, платежи): основная сессия/`kit_developer` и независимый `kit_reviewer`.
- Для реализации UI, включая локальные баги поведения, используй [UI-маршрут](references/ui-workflow.md): `kit_ui_designer`
  по потребности, `kit_ui_developer` для реализации и существующий reviewer.
- Несколько зависимых результатов/неясная архитектура: используй существующий план;
  `kit_planner` нужен для существенной новой декомпозиции, `kit_explorer` — узкого неизвестного.
  Не запускай роли формально. Для делегирования читай [runtime](references/runtime.md).

## Выполнение

1. Зафиксируй критерии и baseline по [Git-workflow](../git-workflow/SKILL.md).
   Его правила владения действуют при параллельной реализации и интеграции.
   При возобновлении плана сверь пункты `[x]` с текущим состоянием, критериями и
   результатами проверок, включая обязательное ревью. Актуальные результаты переиспользуй.
   При расхождении или пробеле проверь только затронутые критерии и при необходимости
   переоткрой пункт. Продолжи с незавершённого результата, чьи зависимости готовы.
2. Объедини связанные изменения в пакеты поведения. Параллельно — не более двух
   пишущих исполнителей, включая основную сессию, и доступных слотов. Области записи
   не пересекаются; конфликтующие проверки с общей БД/портами изолируй или запускай последовательно.
   Для общего API заранее назначь владельца контракта/schema/codegen и дай обеим
   сторонам одну ревизию. Интеграцию ведёт основная сессия либо назначенный владелец.
   Расширение записи согласуется с оркестратором до правок, не с пользователем повторно.
3. Реализуй пакет по TDD там, где он применим по [инженерным правилам](../../../.codex/rules/engineering.md),
   без передачи каждого Red/Green другому агенту. Выполни проверки, включая интеграцию сторон после
   их готовности. Обнови нужные документы: малые правки делает автор, значительный
   согласованный объём — один `kit_documenter`. Для пользовательских инструкций примени
   [правила dev-docs](../dev-docs/SKILL.md#пользовательские-инструкции).
   Подготовь текст истории по `.codex/rules/history.md`.
4. Для обязательного ревью передай одному `kit_reviewer` стабильную область, критерии,
   baseline, применимые правила, результаты проверок и текст истории. В область входят
   существенные docs/config и итоговая интеграция. Не меняй проверяемые файлы параллельно.
   `PASS` закрывает ревью, не заменяя проверки; `FIX` ведёт к исправлениям;
   `INCONCLUSIVE` — к получению недостающих данных и follow-up того же reviewer.
   После PASS новое решение/непроверенное взаимодействие требует адресного ревью,
   включая чистый merge. Одно оформление проверенного содержимого новый цикл не запускает.
5. Исправления возвращай тому же автору, ревью — тому же reviewer. После двух
   раундов без решения/при повторяющейся причине или разногласии подключи одного
   `kit_expert`, затем обоснованную попытку и проверку. Недоступный обязательный
   критерий или неустранённый дефект остаётся открытым; не объявляй успех.
6. Сохрани и проверь историю. Затем обнови прогресс плана один раз на результат;
   `completed` — только после всех критериев, нужных docs, истории и PASS обязательного
   ревью. Для отметки завершения используй уже оформленную запись этого результата;
   самостоятельная правка плана в другом изменении следует правилам истории.

Передавай агентам цель, область записи, критерии, пути и необходимые факты вместо
истории чата, полного плана и копий доступного diff. Подробные логи оставляй в файлах.
Итог: результат, проверки, ограничения и пути истории. При делегировании укажи роли,
запрошенные модели/effort и число раундов. Токены — только из реальной телеметрии.
