# TDD в рабочем цикле

TDD принят для воспроизводимых ошибок и нового/изменённого поведения, которое можно
автоматически проверить. Нормативные инструкции находятся только в
[engineering.md](../codex-kit/.codex/rules/engineering.md); dev-cycle и роли ссылаются
на них. Этот документ объясняет решение, его не нужно читать на каждой задаче.

## Что это даёт и чего не обещает

Тест до реализации заставляет определить ожидаемое поведение и интерфейс; цикл
Red → Green → Refactor включает улучшение структуры после получения работающего
результата. Это соответствует [описанию Мартина Фаулера](https://martinfowler.com/bliki/TestDrivenDevelopment.html).

Промышленные наблюдения показывают возможный выигрыш в качестве, но не гарантируют
ускорения: в исследовании четырёх команд Microsoft/IBM снижение дорелизной плотности
дефектов сопровождалось субъективно оценённым увеличением начального времени разработки.
[Исследование 2008 года](https://research.ibm.com/publications/realizing-quality-improvement-through-test-driven-development-results-and-experiences-of-four-industrial-teams).

Результат зависит от контекста: серия из 12 экспериментов обнаружила у новичков TDD
немного лучшее качество при итеративном подходе test-last и существенное влияние задачи.
[Santos и соавторы, 2020](https://arxiv.org/abs/2011.11942).
Эти результаты о разработчиках не доказывают экономию токенов агентской системы.

## Где применять

| Задача | Подход |
|---|---|
| Воспроизводимая ошибка | Регрессионный тест падает на исходном поведении, проходит после исправления |
| Бизнес-правило, вычисление, валидация, переход состояния | Короткие test-first итерации по наблюдаемым результатам |
| API, конкурентная запись, очередь, миграция | Тест на нужной границе; при необходимости настоящая БД/брокер на изолированном стенде |
| UI | Состояния и взаимодействия проверяются автоматически, внешний вид дополнительно проверяется рендером |
| Чистый рефакторинг | Сначала зелёная защита текущего допустимого поведения; искусственная красная фаза не нужна |
| Docs, косметика, исследовательский прототип | Подходящая проверка без искусственных тестов; исследовательский код ещё не готовая функция |

Недоступность окружения не превращает неподтверждённый Red/Green в выполненный.
Можно подготовить тесты и продолжить допустимую работу, обозначив ограничения;
обязательные проверки и критерии завершения сохраняются.

Подходящий CI Red можно использовать без повторения: нужно проверить совпадение
исходного кода, сценария, входов/зависимостей и причины падения. При несоответствии
или недостатке свидетельств тест запускается до исправления. Green относится уже
к исправленному состоянию; прежний Red его не заменяет.

## Как участвуют агенты

Оркестратор или planner задаёт поведение и критерии. Автор реализации выбирает первый
сценарий и выполняет маленькие циклы TDD в своей сессии. Reviewer проверяет контракт,
смысл assertions, доказательства запусков и границы интеграции после стабилизации пакета.
Создавать отдельного тестировщика или ревьюера на каждую красную фазу не требуется.

Излишняя детализация mocks может закрепить текущую реализацию вместо требований;
копирование результата функции в ожидаемое значение даст ложную уверенность.
Поэтому зелёные тесты сами по себе не заменяют независимое ревью, интеграционные
проверки, нагрузочные измерения и визуальную проверку UI.

Достаточно краткой записи: сценарий/команда, фактическая причина Red, результат Green
и проверки после рефакторинга либо конкретная причина отступления. Отдельные документы,
коммиты и записи истории для каждой микроитерации не нужны. В истории остаётся
законченный пользовательский/технический результат по действующему формату.

## Как оценить пользу

На сопоставимых задачах сравнивать дефекты, доработки после ревью, время и фактическую
телеметрию токенов. Не считать количеством тестов, покрытием или скоростью первой
реализации доказанную эффективность. Полные прогоны выполнять по затронутым границам;
внутри короткого цикла обычно достаточно целевого теста.

Внедрение меняет инструкции комплекта. Прикладной код и тесты DMC не изменены,
автоматического охвата существующего проекта тестами это не создаёт.
